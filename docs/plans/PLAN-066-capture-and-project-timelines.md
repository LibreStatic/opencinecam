# OCC-PLAN-066: Capture and project timelines

## 1. Objective

Implement the approved H4 rational capture/project, interval, pause/off-speed and related timing scope. Begin with the real timelapse timestamp regression; retain all later H4 and H1–H5 requirements.

## 2. Why This Plan Exists

Independent ffprobe and decoder evidence from build/implementation-h3-operation proves that the old timelapse path compressed timestamps without the required project-cadence frame selection.

## 3. Prerequisites

OCC-PLAN-015; current operation checkpoint with 324 passing host tests, 91 instrumented cases and preserved bad-cadence media.

## 4. Required Reading

ADR-0033, requirements OCC-PRO-001/007, proposal VID-01/timelapse and current service, Camera2, GLES, encoder/muxer and timecode code.

## 5. Inputs

Preserved operation source and MANUAL_TIMELAPSE.mp4/media-packets.json; public API30 codec/camera fixture; physical capture/audio/editor qualification still required.

## 6. Deliverables

Correct capture/project clocks, connected configurable intent and actual reporting, bounded recording paths, real media tests and reversible source evidence.

## 7. In Scope

Full H4 timeline scope: interval selection, rational capture/project clocks, off-speed, pause/resume, monotonic A/V/timecode relationships and related media acceptance.

## 8. Out of Scope

This plan alone does not complete H4 photography/media library work, remaining H3 monitors/audio or H5. No final APK before the entire goal passes.

## 9. Architecture

ADR-0033; select real frames before encoding and assign rational project timestamps independently from source arrival time. Preserve source/codec provenance and missed-interval reporting.

## 10. Implementation Steps

1. Preserve and test the operation baseline.
2. Implement pure selection/rational clocks and bounded GLES recording.
3. Connect interval/project preferences, actual frame limits and reporting.
4. Validate encoded samples and decoder output.
5. Continue regular off-speed/pause/A/V/timecode and physical/editor gates.

## 11. State and Data

Reuse the current Camera2/GLES producer and immutable per-take capture configuration; do not add full-frame CPU copies or discard interdependent encoded frames.

## 12. Failure Handling

Malformed clocks/settings fail before capture. Codec or frame-accounting failure finalizes unsuccessfully and deletes incomplete output, retaining diagnostics.

## 13. Tests

Pure tests cover density, late frames, exact rational PTS, invalid timestamps and limits. Instrumentation checks real service media, codec choice, exact output sample cadence and stop/recovery.

## 14. Documentation Updates

## AAC waveform/tail diagnosis (revision 9; production correction still open)

The 437-frame count deficit in the shared-epoch checkpoint was not harmless padding. A new real MediaCodec/MediaMuxer probe encodes known swept PCM, retains exact source bytes and emitted packet records, and independently decodes every file with FFmpeg. Its matrix covers 48 kHz mono (52661 and exact-block 52224 source frames), 44.1 kHz stereo (52661 frames), EOS on the last data buffer versus a separate empty buffer, and zero versus 4096 explicitly experimental trailing zero frames. The zeros exist only in the test, not in production audio or captured-source counts.

On emulator-5680 / API30 / c2.android.aac.encoder, both legal EOS forms produce the same result. Without experimental zeros, the decoded signal lags the source by 2048 frames and loses 2485 source-tail frames for 52661-frame inputs, or 2048 for the exact-block input. The decoder's 52224-frame result includes the leading delay; it is not 52224 preserved source frames. AAC output packet counts equal independently extracted MP4 packet counts, so the diagnostic locates the missing content before a supposed mux-packet discard. This is measured decoded-waveform alignment, not a microphone-latency calibration or a claim that every vendor encoder behaves alike.

With 4096 experimental zeros, all six matrix files preserve the full known source at the measured 2048-frame lag, with channel correlations above 0.98. They still contain 1611 or 2048 trailing decoded frames and retain the leading delay: they are not gapless or correct A/V outputs. Production must not adopt a hard-coded universal priming value or silently add zeros merely to pass a packet-count check.

Reusable evidence: app/src/androidTest/java/com/librestatic/opencinecam/AacTailProbeTest.kt; tools/analyze_aac_tail.py and its tests; build/implementation-h4-aac-tail/VERIFICATION.txt. The analyzer distinguishes matched source coverage from gapless trimming, detects missing starts/tails even when total lengths agree, checks channels separately and offers an explicit --require-source-coverage gate. That gate fails the unpadded matrix (exit 2); successful diagnostic collection is not successful audio qualification.

Next implementation must couple explicit codec drain/source-frame accounting to verified priming and container start/end trimming, preserve capture-domain A/V offsets, and test short/partial/exact-block takes, rates/channels, actual service finalization and independent playback. The output descriptor is duplicated before queuing work, so caller timeout/closure cannot revoke the queued owner's descriptor. The drain thread is created and started before commit but waits on the same terminal decision before accessing native state. If cancellation wins, that worker exits without touching codecs; the GL owner joins it before cleanup and releases its descriptor before clearing the preparation lease. Pipeline close also participates in the cancellation decision. Committed resources retain the existing drain/GL/audio retirement protocol.
